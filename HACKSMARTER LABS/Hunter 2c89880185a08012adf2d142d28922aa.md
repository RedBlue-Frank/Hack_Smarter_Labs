## Techniques to try:

### Login error behaviour (most common)

`Submit:`

* **Known-bad username + random password**
* **Candidate username + same random password**

`Look closely at:`

* Error message text
  * _“Invalid username”_ vs _“Invalid password”_
  * _“User does not exist”_ vs _“Incorrect credentials”_
  * HTTP status codes
  * Response body length

Even subtle differences (1–2 words, HTML length) are enough.

### Timing-based enumeration (Werkzeug apps are often vulnerable)

`Some apps:`

* Check **username first**
* Then hash/verify password **only if user exists**

`Result:`

* Valid username responses take **slightly longer**

`How to test:`

* Send the **same password** for every username
* Measure response time over **multiple requests**
* Average the timings

If one username is consistently slower → **valid user**

### Password reset / forgot password (if present)

`If there is:`

* _“Forgot password?”_
* _“Reset password”_

`Test each username/email:`

* Valid users often return:
  * “Password reset sent”
* Invalid users:
  * “User not found”

Even if the message is generic, timing and response size can still differ.

### Registration collision (if signup exists)

`Try registering:`

* Existing username → _“Username already taken”_
* Non-existing → proceeds further

This is clean confirmation if exposed.
