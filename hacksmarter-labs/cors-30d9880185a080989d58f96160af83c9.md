# CORS

## **Understanding SOP & CORS**

The web is designed to be open, but also secure. By default, browsers enforce the SOP to prevent malicious interference between websites.

* **The Concept:** Imagine you have two open tabs. Tab A is your online bank (`bank.com`), and Tab B is a malicious site (`attacker.com`).
* **The Danger:** Without SOP, JavaScript running on Tab B could send a request to `bank.com`, read your transaction history, and send it to the attacker.
* **The Protection:** SOP ensures that scripts running on one "origin" cannot read the data returned from a different "origin."

**What defines an "Origin"?**

Two URLs share the same origin only if they have the exact same:

1. **Protocol** (e.g., `https://`)
2. **Domain** (e.g., `example.com`)
3. **Port** (e.g., `:443`)

### **The Exception: Cross-Origin Resource Sharing (CORS)**

While SOP is the "lock," **CORS** is the "key." Modern web applications often need to share data between different domains (for example, a website at `example.com` fetching user data from an API at `api.example.com`).

CORS is a mechanism that allows a server to explicitly relax the SOP. It works through **HTTP Headers**.

1. **The Request:** When a browser makes a cross-origin request, it adds an `Origin` header to identify where the request is coming from.
   * `Origin: https://attacker.com`
2. **The Response:** The server reviews the origin. If it approves, it sends back a specific header permitting the browser to read the response.
   * `Access-Control-Allow-Origin: https://attacker.com`
3. **The Browser's Role:** If the browser sees this header, it allows the JavaScript to read the data. If the header is missing or doesn't match, the browser blocks the data.

## **Why This Matters (Impact)**

Why do we care about CORS during a penetration test? It is not just a technical error; it is a direct pathway to data theft.

### **1. Data Exfiltration**

This is the primary consequence of a CORS vulnerability. If an attacker can trick the server into accepting their malicious origin, they can proxy the victim's authenticated session.

* **Scenario:** A victim visits a malicious site.
* **Action:** The malicious site forces the victim's browser to send a request to the vulnerable intranet portal.
* **Result:** Because of the CORS misconfiguration, the malicious JavaScript can read the confidential JSON response (containing emails, PII, or financial data) and forward it to the attacker's server.

### **2. Session Hijacking**

In some modern Single Page Applications (SPAs), session tokens (like JWTs) or API keys are returned in the response body of a `/login` or `/user/profile` endpoint. If an attacker exploits CORS to read this specific response, they can steal the user's active session token and take over the account entirely.

### **3. CORS vs. CSRF: The Distinction**

Beginners often confuse these two client-side attacks.

* **CSRF (Cross-Site Request Forgery):** Focuses on **State Changes**. The attacker forces the victim to perform an action (like "Delete Account" or "Transfer Money"). The attacker _cannot_ see the response; they only care that the action happened.
* **CORS (Cross-Origin Resource Sharing):** Focuses on **Data Theft**. The attacker forces the victim to fetch data so the attacker can _read_ it.

## **Common Misconfigurations**

Developers often misconfigure CORS in an attempt to make their application "just work," unintentionally destroying the security model.

### **Scenario A: Reflected Origin (The "Mirror")**

This occurs when the application blindly trusts the client. The server-side code reads the `Origin` header from the incoming request and simply copies it into the `Access-Control-Allow-Origin` response header.

* **Vulnerable Configuration:** "If a request comes in, just echo the origin back so the browser accepts it."
* **The Danger of Credentials:** This becomes critical when the server also sends `Access-Control-Allow-Credentials: true`. This header tells the browser, "Yes, send the user's cookies and session tokens with this request."
* **Exploit:** An attacker hosts a script on `evil.com`. The victim visits it. The browser sends the request with cookies. The server reflects `evil.com` and allows credentials. The attacker steals the data.

### **Scenario B: Weak Regex (The "Partial Match")**

Developers may try to implement a whitelist using Regular Expressions (Regex) but fail to anchor the search correctly.

* **Intended Whitelist:** Allow `example.com`
* **Flawed Logic:** The code checks if the origin string _contains_ `example.com`.
* **The Bypass:** An attacker registers the domain `example.com.attacker.net`. Because the string "example.com" appears inside the malicious domain, the insecure regex allows it.

### **Scenario C: The Wildcard (\*)**

The server is configured to allow access to everyone using the wildcard symbol:`Access-Control-Allow-Origin: *`

* **The Limitation:** For security reasons, browsers will **disable** the use of cookies/credentials if the server uses a wildcard . You cannot send `Access-Control-Allow-Credentials: true` combined with a wildcard.
* **The Risk:** While this prevents direct cookie-stealing exploits, it is still dangerous if:
  1. The site is accessible on an internal network (permitting external attackers to map internal intranets).
  2. The application uses custom authentication headers (like `Authorization: Bearer <token>`) instead of cookies, which may sometimes bypass this restriction depending on how the client is coded.

## **Testing Methodology**

Knowing the theory is great, but how do we actually _find_ these bugs in the wild? You can't just guess; you have to actively probe the application.

To test for CORS, we use a technique called **Origin Reflection Testing**.

### **The Tool of Choice**

You cannot test for CORS effectively using just a web browser's Developer Tools. You need an **Intercepting Proxy** like **Burp Suite** or **Caido**. These tools allow you to pause a request in mid-air, modify the headers, and send it to the server to see how it reacts.

### **The Workflow**

Here is the exact step-by-step process we use on a real engagement:

**Step 1: Capture a Legitimate Request**

Browse the application normally. Look for requests that fetch sensitive data (API calls, JSON files, user profiles).

* _Why?_ CORS only matters if there is sensitive data to steal.

**Step 2: Send to Repeater/Replay**

Send that request to your tool's manual testing tab (Repeater in Burp, Replay in Caido). This lets you modify the request and send it as many times as you want.

**Step 3: Add the `Origin` Header**

This is the key step. We need to see if the server trusts us.

* **Test A (The Basic Probe):** Add `Origin: https://evil.com` to your request headers.
* **Test B (The Subdomain Probe):** If the site is `example.com`, try `Origin: https://example.com.evil.com` to test for weak regex.

**Step 4: Check the Response**

Send the modified request and look at the **Response Headers**. We are looking for two things:

1. **Reflection:** Did the server respond with `Access-Control-Allow-Origin: https://evil.com`?
2. **Credentials:** Did the server _also_ respond with `Access-Control-Allow-Credentials: true`?

### **The "Golden Rule" of CORS Testing**

If the server reflects your malicious origin **AND** allows credentials (`true`), you have a high-severity finding.

If the server reflects your origin but `Access-Control-Allow-Credentials` is missing or `false`, the exploit is much harder (and often impossible) because the browser won't send the user's cookies.

We test by lying to the server about where we are coming from (via the `Origin` header) and seeing if the server is gullible enough to believe us.

### **Prevention and Defense**

* **Avoid Reflection:** Never programmatically reflect the `Origin` header into the `Access-Control-Allow-Origin` response.
* **Strict Whitelisting:** Use a static list of trusted domains.
* **Avoid Wildcards with Credentials:** Browsers actually block the combination of `Access-Control-Allow-Origin: *` and `Access-Control-Allow-Credentials: true`.
* **Don't use `null`:** Avoid supporting the `null` origin.
